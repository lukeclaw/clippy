# Privacy

A clipboard manager sees every password you copy. This is the one area where the
"personal tool, keep it simple" principle doesn't apply — a history file full of
plaintext credentials is a real problem regardless of who's running it.

## Marker types — settled

macOS applications signal intent through advisory pasteboard types, documented at
[nspasteboard.org](https://nspasteboard.org). Password managers rely on them.
Honouring them is not optional.

| Marker | Meaning | Clippy's behaviour |
| --- | --- | --- |
| `org.nspasteboard.ConcealedType` | Confidential | Memory only, redacted, 5-minute TTL |
| `org.nspasteboard.TransientType` | Will vanish in seconds | Never recorded |
| `org.nspasteboard.AutoGeneratedType` | User didn't intend to copy this | Recorded, flagged |
| `org.nspasteboard.RestoredType` | A clipboard manager put this back | Never recorded |

Markers are checked before anything else touches an item — before dedup, before
storage, before the UI ever sees it.

## Concealed content — settled

Chosen deliberately over the two alternatives:

**Kept in memory, redacted, evicted after 5 minutes. Never written to disk.**

- *Not dropped entirely*, because "paste the password again" is a real need and a
  history with silent gaps is confusing.
- *Not encrypted on disk*, because that means key management, Touch ID
  integration, and a keychain entry — real complexity, for a tool where the
  in-memory window covers the actual use case.

Redaction is a property of the model, not the view. `ClipItem.displayPreview()`
returns dots for a concealed item regardless of caller. No UI code should be able
to leak a credential by forgetting a check.

## What touches disk

Written:

- Text and rich-text clips, in plaintext, in SQLite
- Image and file payloads, as blobs
- Source bundle IDs and timestamps
- The paste log — see below

Never written:

- Anything marked concealed
- Anything marked transient or restored
- Any paste of a concealed clip, including its metadata

## The paste log — settled

Every paste is recorded: which clip, into which application, when, which
transforms were applied, and whether it succeeded. `clippy log` reads it.

This is a different category from everything else here. The rest of the database
is **content you chose to copy**; this is **behaviour** — a durable record of
where your clipboard contents went and when. It is worth naming as a deliberate
choice rather than letting it arrive as a side effect of a feature.

Two rules constrain it:

**Concealed clips are never logged at all.** Not even without their content.
"Pasted into Slack at 14:32" is still a record that a credential went somewhere,
and the whole point of the concealed policy is that such an event leaves no trace
on disk.

**The log denormalises a preview of the clip** rather than joining back to
`items`. Images are still evicted under the blob budget, so an event that joined
would silently become unreadable when its clip aged out. The copy is deliberate
duplication: it means an event stays meaningful for as long as it exists.

The log has no retention limit of its own. It is small — a row is a few hundred
bytes — and truncating a history of actions to save kilobytes would be a poor
trade. Delete `~/Library/Application Support/Clippy/history.db` to clear
everything, or `DELETE FROM paste_events` to clear only the log.

## Ordinary history is not encrypted — settled

Deliberate. The realistic threat is a credential sitting in a database for
months; that's addressed by never persisting concealed items. Encrypting the rest
defends against an attacker with filesystem access, at which point the clipboard
database is far from the biggest problem — and the key has to live somewhere on
the same machine anyway.

Revisit if the machine stops being solely yours.

## Clippy ignores itself — settled

Clips whose source is Clippy are never recorded. Prevents feedback loops and
keeps the tool's own operation out of the history.

## No telemetry — settled

Nothing is sent anywhere. There is no network code in this project, and adding
any should require a reason written down here first.

## Password managers are denylisted — settled

`SensitiveSources` lists password-manager bundle IDs whose clips are **never
recorded**, whatever markers they set or fail to set.

The marker convention is cooperative, which means trusting the source to declare
itself. That works for the apps that bother. The denylist does not depend on it,
and covers the category where a miss is most expensive. Dropped outright rather
than kept memory-only: a password manager's clipboard has no value in a history,
and not recording it is the only handling with no failure mode.

Being a denylist, it is inherently incomplete — see the gap below.

## File permissions — settled

The directory and blob store are `0700`; `history.db` and its `-wal` and `-shm`
files are `0600`. Applied on every open, so an install created before this
existed is tightened rather than left as it was.

These were previously created at the process umask — `755` and `644`,
world-readable. In practice they were unreachable, because
`~/Library/Application Support` is itself `700`. The protection was real but
accidental: it held only as long as nothing changed a parent directory and
nothing copied the files elsewhere.

## Known gap

Narrowed by the denylist, not closed.

Credentials that arrive from somewhere other than a password manager are
indistinguishable from ordinary content: an API key copied out of a `.env` file,
a token from a web dashboard, a 2FA code, a password pasted through Slack. All of
it is stored in plaintext.

**This got worse with D17.** Under the old 1000-item cap a copied secret aged out
within days of normal use. Text history is now kept forever, so anything that
slips through stays on disk indefinitely. That is a real increase in exposure and
it arrived as a side effect of a storage decision rather than a considered one.

Two things bound the risk, neither of them a fix: FileVault covers the machine at
rest, and the store is readable only by the account that owns it. Neither helps
against a process running as you, which is the realistic threat.

Mitigations available today: ⌫ in the panel deletes an item, and deleted rows are
genuinely removed from the file — verified against the raw bytes, not assumed.
Deleting `~/Library/Application Support/Clippy/` clears everything.

The open idea is content heuristics — treating high-entropy strings and known
key prefixes (`sk-`, `ghp_`, `AKIA`) as concealed regardless of source. Imperfect
by nature, and not yet decided.
